# 게임 최적화 핵심 성과

**Before → 적용 기술 → After | 2026-09-23 정리**

## 한눈에 보는 결과

화질이나 게임 규칙을 줄이는 대신, **이미 끝낸 일을 반복하지 않고 필요한 일만 처리하도록** 바꿨다.

- **게임 화면:** 맵 전체를 반복 검색하던 작업을 줄이고, 비슷한 물건을 묶어 그리도록 개선했다. PC 3인 고정 장면에서는 **약 77 → 111FPS**를 확인했다.
- **메모리:** 화면 안내와 리플레이 처리에서 불필요한 임시 데이터 생성을 줄였다.
- **서버:** 빈 방에서도 쉬지 않고 돌던 실행 루프를 실제 게임 처리 속도에 맞췄다. 같은 서버 자원의 낭비를 줄이는 변경이며, **서버 요금 자체가 얼마나 줄었는지는 아직 측정하지 않았다.**

FPS(Frames Per Second)는 1초에 만드는 화면 수로 높을수록 부드럽다. CPU(Central Processing Unit)는 계산을 담당하는 장치이며, 아래의 1코어는 계산 장치 하나를 계속 사용하는 정도를 뜻한다. HUD(Head-Up Display)는 타이머·아이템 안내처럼 게임 화면 위에 표시되는 정보다. 임시 메모리 할당(GC Allocation)은 나중에 자동 정리해야 하는 데이터의 생성량이다.

> 포함 기준: 원본 게임 코드 `develop`의 기준 커밋 `2e95f0f1f`에 반영된 변경만 기재했다. 실제 서비스에 배포된 파일의 버전까지 확인했다는 뜻은 아니다. 시험 사본에만 있는 최신 후보는 제외했다. 아래 버전명은 이해를 돕기 위한 문서용 단계명이다.

## 1. 게임 화면: 무엇을 바꿔 FPS를 높였나?

| 단계 | Before: 낭비하던 일 | 적용한 기술을 쉽게 설명하면 | After: 확인한 변화 |
|---|---|---|---|
| C1 · 물건 목록 재사용 | 하이라이트를 준비하려고 일반 경기 중에도 맵 전체 물건을 매 프레임 다시 찾음 | 처음 준비한 물건 목록을 재사용하고 녹화에 필요한 물건만 조회 **(참조 캐싱, Reference Caching / 전체 씬 검색 제거)** | **44.15 → 65.14FPS, +47.5%** |
| C2 · 캐릭터 재검색 제한 | 리플레이용 캐릭터가 모두 준비돼도 계속 전체 검색 | 준비가 끝나면 검색을 멈추고, 참가자가 바뀌거나 늦게 도착하면 다시 확인 **(상태 기반 조건부 갱신, Conditional Update)** | **71.26 → 79.69FPS, +11.8%** |
| C3 · 정지 물건의 갱신·보간 중단 | 이미 멈춘 물건에도 갱신 및 부드러운 이동 계산이 남아 있음 | 멈추면 계산을 쉬고 새 위치가 도착하면 즉시 재개 **(FixedUpdate 비활성화 / Rigidbody 위치 보간, Interpolation 중단)** | **80.61 → 95.35FPS, +18.3%** |
| C4 · PC GPU 묶음 렌더링 | 수많은 물건을 그리기 위한 준비·제출 작업이 많음 | 비슷한 물건의 그리기 작업을 GPU에서 묶어 처리 **(GPU Resident Drawer / GPU 인스턴싱, GPU Instancing)** | **76.95 → 110.74FPS, 약 +43.9%**. 그리기 묶음 **(Batches)** 약 **16,000 → 2,985회** |

**비교 조건:** C1·C2는 RTX 4070 Laptop을 사용한 Unity 에디터 경기에서 각 30초×3회의 중앙값이다. 두 실험의 화면 주사율 조건은 다르다. C3는 같은 에디터의 정지 물건 6,140개 장면에서 전후 각 20초×2회의 평균이다. C4는 Windows 일반 빌드·1920×1080·3인 정지·고정 시야에서 각각 4회 평균 FPS의 중앙값이다(원래 범위: 74.51~78.17 → 109.35~111.97).

**각 행은 독립된 전후 비교다.** 44FPS에서 시작해 모든 변경을 더한 결과가 111FPS라는 의미는 아니며, 개선율도 서로 합산하지 않는다. C4의 화면 해상도와 물건·주광원 그림자는 유지했다. 정지 물건은 보이지 않게 만들거나 충돌을 없앤 것이 아니다.

C3의 FPS 수치는 스크립트 갱신 중단에 더해 **남아 있던 위치 보간까지 중단한 추가 변경**의 비교다.

**그리기 용어:** 드로우콜(Draw Call)은 CPU가 GPU에 보내는 그리기 명령이다. 배칭(Batching)은 그릴 대상을 묶어 처리하는 기법이고, GPU 인스턴싱(GPU Instancing)은 같은 메시·재질을 쓰는 여러 물체를 묶어 그리는 방식이다. C4에 기록된 수치는 Unity의 **Batches 지표**이므로 드로우콜을 별도로 측정한 정확한 횟수로 바꿔 부르지는 않는다.

## 2. 반복 계산과 메모리 낭비는 어떻게 줄였나?

| 단계 | Before | 적용 기술 | After |
|---|---|---|---|
| M1 · HUD 안내 정보 조회 | 화면에 카테고리 이름을 표시하면서 전체 상품 정의를 반복 재구성 | 표시할 이름만 읽고, 상품 정의 생성은 필요한 초기화·배정 경로에 유지 **(조회·초기화 분리 / GC Allocation 감소)** | HUD 임시 할당 **18,801 → 24바이트/프레임**. 해당 갱신 시간 **0.220 → 0.067ms** |
| M2 · 리플레이 ID 전용 조회 | 물건의 이름표(ID)만 필요해도 위치·회전까지 계산 | ID만 조회하는 경로를 분리하고 실제 녹화에는 기존 좌표 계산 유지 **(ID-only Lookup / 불필요한 Transform 조회 제거)** | ID 수집 **0.363 → 0.275ms**, 약 **24.2% 감소** |
| M3 · 리플레이 중간 복사 제거 | 리플레이 압축·복원 중 같은 데이터를 새 배열로 여러 번 복사 | 불필요한 중간 복사를 제거하고 기존 데이터·압축 형식 유지 **(중간 버퍼 복사 제거, Buffer Copy Elimination)** | 압축 임시 할당 **4.23 → 3.44MB/회**, 복원 **6.47 → 4.88MB/회** |

M1은 개발 프로파일 표본, M2는 같은 경기의 교차 측정이다. M3는 동일 PC의 .NET 합성 데이터 시험(6인·3클립·프레임당 물건64개)이며 MB는 100만 바이트 기준이다. **이 수치를 전체 게임 FPS 상승이나 상시 메모리 사용량 감소로 바꾸어 표현하지 않는다.**

플레이어 입장에서 화면 정보와 리플레이 내용은 그대로이고, 그 결과를 만들기 위한 반복 작업과 임시 데이터가 줄어든 것이다.

## 3. 서버: 무엇을 바꿔 계산 비용을 낮췄나?

### S1 · 게임 처리 속도에 맞춰 서버 실행

**Before:** 빈 방에서도 서버의 바깥 실행 루프가 초당 약 13,000~15,000회 돌면서 CPU 약 1코어를 사용했다. 이것이 실제 게임 판정을 그만큼 자주 한다는 뜻은 아니다.

**적용:** 전용 서버의 실행 상한을 실제 게임 처리 속도인 **초당 64회**에 맞췄다 **(서버 루프 프레임 제한·페이싱, Frame Rate Limiting / Frame Pacing)**. Unity의 `Application.targetFrameRate`를 실제 네트워크 틱 속도 **(Tick Rate)**에 맞춘 것이다. 틱은 게임 상태를 계산하는 한 번의 처리 단위다. 플레이어 화면의 FPS 제한을 낮춘 것이 아니며, 실제 게임 판정 속도도 유지했다.

| 확인한 항목 | Before → After | 의미 |
|---|---|---|
| 같은 EC2 빈 방의 원인 확인 시험 | 무제한 **1.0032코어 → 60회 제한 0.0517코어** | 불필요한 반복 실행을 제한했을 때 CPU 약 **94.8% 감소**를 확인한 대조 시험 |
| 실제 제품에 넣은 값 | 무제한 → **실제 틱에 맞춘 64회/초** | 위의 60회 대조값과 제품 적용값은 구분 |
| 64회 적용본의 3인 정지 경기 | **0.21~0.23코어**, 실제 판정 **64회/초 유지** | 게임 처리 속도를 유지하면서 실행되는 것을 확인 |

**서버 비용의 의미:** 불필요한 계산을 줄여 다른 방을 처리할 여유를 만든 것이다. EC2를 같은 크기·같은 시간 동안 켜두면 이 변경만으로 청구요금이 자동 감소하지는 않는다. 서버 크기나 대수를 줄일 수 있는지는 다중 방·최대 부하 검증 후 결정해야 한다.

최초에 관측한 방당 약 1.1코어와 이후 약 0.22코어는 인원·이동·버전 조건이 달라, 그 차이 전체를 최적화 절감률로 계산하지 않았다. **보장 가능한 최대 동시 접속자 수와 월 요금 절감액은 아직 확정하지 않았다.**

## 4. After: 지금 말할 수 있는 최종 결론

| 구분 | 확정해서 설명할 수 있는 성과 |
|---|---|
| 화면 부드러움 | 반복 검색·정지 물건 계산·PC 그리기 작업을 줄였고, 위의 각 비교 장면에서 FPS 상승을 확인했다. |
| 내부 처리 효율 | HUD·리플레이에서 반복 계산과 임시 메모리 생성을 줄였다. |
| 서버 효율 | 필요 이상으로 돌던 서버 루프를 제한하고 실제 게임 판정 속도64회를 유지했다. |
| 기능 보존 | 관련 자동 검사에서 물건 이동 재개·집기·던지기·배치, 하이라이트 준비와 HUD 조회의 기존 동작을 확인했다. 모든 장면·모든 환경의 무결점을 보증하는 뜻은 아니다. |

**아직 주장하지 않는 것:** 모든 상황에서 안정적120FPS, 핑 개선, 특정 최대 접속자 수 보장, 월 서버 요금 절감률. 최신 FPS 확정 비교는 사용자 Unity 작업 종료 후 별도로 진행한다.
