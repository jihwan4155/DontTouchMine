# WebGL 로비 렌더링 최적화 — 2026-09-10

## 범위와 판단 기준

Host 모드와 게임 기능을 유지한다. 사용자는 3D 선명도 자동 조절을 허용했고, 부드러운 플레이를 우선한다. 브라우저·Windows 설정 변경은 요구하지 않는다. UI 캔버스 해상도, 조명 수, 물리·네트워크 tick과 게임 규칙은 변경하지 않는다. 이후 사용자가 그림자 비교의 3번을 선택하여 WebGL 실시간 그림자는 전체 비활성화한다.

## 적용 내용

- `WebGlAdaptiveResolution`: WebGL 플레이어에서만 현재 URP 설정을 복제하고 3D renderScale을 원본의 50~100% 사이로 조절한다. 2초 동안 지속적으로 느리면 10%p 낮추고, 10초간 여유가 유지되면 5%p 복구한다. 목표는 사용자 FPS 상한과 60 중 낮은 값이다. UI Overlay는 원래 출력 해상도를 사용한다.
- 단발성 로딩 지연과 비활성 탭은 배율 하락 근거에서 제외한다. 10FPS 미만의 지속적인 저성능은 조절 대상에 포함한다.
- `WebGL` 품질 프로필은 기존 PC 프로필을 바탕으로 주광원·추가 광원의 실시간 그림자와 Soft Shadows를 비활성화한다. Screen Space Shadows 기능도 비활성화한다. PC 기본 프로필과 Standalone 기본 선택, SSAO, 조명과 Forward+는 유지한다. 설정창의 그림자 품질은 기존대로 저장·표시만 하고 렌더링에는 적용하지 않는다.
- 일반 `WebBuild`는 에디터에 남은 옵션과 무관하게 IL2CPP OptimizeSpeed / WASM RuntimeSpeed를 명시한다. 기존 FAST_BUILD 경로와 설정 복원은 유지한다.
- 로비 Opaque Texture 비활성화 한 줄은 이번 실험 이전부터 작업 브랜치에 있던 변경이다. 이번 개선 수치 전체를 이 변경의 효과로 해석하지 않는다.

## 유효한 측정과 한계

환경: 현재 PC, AC 전원, Unity 6000.3.22f1, Chromium 기반 Codex 내부 브라우저, Intel Arc / ANGLE D3D11, WebGL Host 1명, 로컬 빌드, 캔버스 1920×1200, FPS 상한 120. Unity 빌드와 성능 측정을 동시에 실행하지 않았다.

동일 로비에서 실제 품질 이름·renderScale·출력 크기와 프레임 시간을 기록했다. 첫 교차 실험의 원본은 38.37~47.04FPS, 자동 배율 단독은 49.63FPS였다. 이후 단독 반복은 56.24 / 60.91FPS, 화면 공간 그림자 조합은 69.03 / 69.19FPS였다. 단, 이 구간에는 브라우저 표시 영역 크기 변경이 있어 **69FPS를 최종 제품의 보장 수치로 사용하지 않는다.**

화면 영역을 1280×720으로 명시적으로 고정한 뒤, 같은 카메라 위치에서 최종 후보 → 원본 → 최종 후보를 재측정했다. 각 30초 표본이며, 출력 캔버스는 모두 1920×1200이었다.

| 조건 | 평균 FPS | p95 프레임 시간 | p99 | 33.3ms 초과 비율 |
|---|---:|---:|---:|---:|
| 최종 후보, 첫 표본 | 56.63 | 25ms | 51ms | 1.65% |
| 원본, 배율 1.0 | 50.94 | 30ms | 36ms | 1.96% |
| 최종 후보, 반복 | 67.32 | 21ms | 23ms | 0.00% |

이는 고정 카메라의 로비 표본이며, 전체 경기·다른 PC·다중 플레이의 60FPS 보장이 아니다. 첫 후보 표본에 큰 프레임이 남았으므로 모든 끊김이 제거됐다고 단정하지 않는다. 최종 플레이어 재검증 결과는 아래에 별도 기록한다. 최종 플레이어는 로컬 HTML의 JS draw-callback 계측만 사용했으며, 해당 프레임 표본에는 마우스 잠금 우회를 적용하지 않았다.

### 해석에서 제외한 실험

이전 `structural-corrected-summary.json`과 `structural-scale-summary.json`에는 품질 프리셋 YAML 삽입 위치 오류가 있었다. Unity가 해당 프리셋을 읽지 않았으므로 원래 PC 설정이나 실제 URP 배율 대조로 사용할 수 없다. 파일에는 경고를 붙였으며, 그때의 55→72FPS를 이번 제품 개선 수치로 인용하지 않는다.

화면 공간 그림자 단독은 43.40FPS로 인접 원본보다 빨라지지 않았다. 조합의 반복 실측을 근거로 채택했다. 브라우저 rAF 대조는 58.36FPS/p95 20ms였으나, 사용자 FPS 설정 의미를 바꾸지 않기 위해 제품의 프레임 스케줄러는 변경하지 않았다. 조명·그림자 제거, 렌더러 비활성화 등의 진단은 제품 변경에 포함하지 않는다.

## 병목 해석

확인된 큰 비용은 로비의 클라이언트 렌더링이다. 픽셀 수와 그림자 처리 변경에 프레임 시간이 반응한다. 원본 표본의 일반 Behaviour Update 약 1.27ms, PhysicsFixedUpdate 약 0.32ms만으로 26ms 전후의 전체 프레임 시간을 설명할 수 없다. 다만 이 두 구간은 Fusion의 모든 업데이트를 포함하지 않으므로 서버 시뮬레이션 비용이 없다고 주장하지 않는다.

이 결과만으로 Host를 교체하거나 EC2 CPU를 늘리는 결정을 내릴 근거는 없다. 별도 서버가 있어도 플레이어 노트북의 픽셀·그림자 렌더링 비용은 남는다. 현재 구현은 그 비용을 게임 자체에서 줄이는 조치다. 실제 렌더링에는 배율을 낮춰도 그대로인 그림자 맵 생성과 렌더러 처리 비용이 남는다. 따라서 이번 측정은 60FPS 고정이나 모든 환경의 끊김 제거를 입증하지 못했다.

## 검증

- EditMode 19개 통과: 배율 정책·복구·FPS 상한·로딩 지연·지속 10FPS 미만, WebGL/PC 조명 설정 동일성, 기존 설정 적용, 로비 배칭 안전성.
- 진단 플레이어에서 로비 생성, 물체·조명·UI 표시, 이동 입력 확인.
- 진단 코드 제거 후 최종 플레이어 빌드 성공: `adaptive-final-20260910`, RuntimeSpeed, 1,383.62초. 첫 코드 재생성을 포함한 로컬 빌드이며, 증분 CI 빌드 시간의 측정값은 아니다. 최종 플레이어의 로비 생성·표시 및 프레임 재확인 완료. 안정된 30초 표본은 52.34FPS / p95 23.3ms / p99 27ms / 33.3ms 초과 0.13%였다. 캔버스 1920×1200, 브라우저 1280×720, 가시성·포커스 유지 조건이다. 초기 카메라 방향이 위 대조 표와 달라 50.94→52.34를 직접 개선율로 계산하지 않는다. 첫 자동 표본은 씬 로딩과 겹쳐 제외했다.
- 최종 플레이어에서 설정 열기·닫기와 로비 복귀를 확인했다. 자동 입력 도구의 마우스 잠금 처리 제약 때문에 이 기능 확인 구간의 로컬 HTML에서만 pointer lock을 우회했다. 배포용 HTML/입력 코드에는 우회를 넣지 않는다.
- 전체 경기 전환·집기·던지기·배치 및 서로 다른 PC의 3~6인 실전 회귀를 완료했다고 주장하지 않는다. 게임 판정·물리·네트워크 소스는 이번 변경에서 수정하지 않았다.
- 로컬 실행에는 Backend Offline, 중복 EventSystem, HostTransferConfirmPanel의 missing-script 경고가 관찰됐다. 이 보고서는 해당 경고의 해결을 포함하지 않는다.

## 복구

- 자동 조절만 끄려면 `WebGlAdaptiveResolution`의 WebGL 설치를 제거한다. 컴포넌트 비활성화 시 복제 전 파이프라인을 복원한다.
- 그림자 처리도 원복하려면 QualitySettings의 WebGL 기본 프로필을 `PC`(원본 인덱스 1)로 바꾼다. 기존 PC 렌더러/파이프라인은 보존돼 있다.
- 두 변경을 모두 원복해 다시 빌드하면 원래 고정 배율 렌더링으로 돌아간다.
- 측정용 소스·이미지·JSON은 작업 공간 `.build/lobby-profiler/`에 보관한다. 배포 에셋에는 진단 C#·실험 프리셋을 포함하지 않는다.

## 최종 추가 대조 및 마감 결과 (17:43 KST)

사용자의 30분 이내 보고 요청에 맞춰 추가 대조와 정리를 마쳤다. 극단적인 저해상도 변경은 채택하지 않는다. 소스는 기본 배율 1.0, 자동 조절 하한 0.5를 유지한다. 최종 플레이어·두 에셋 대조 빌드의 WASM SHA-256은 모두 `a8ffb4c39ccb7e05c8beeab5b29d059bf29a11cc5f30394277cccc1a8f4d2c6d`로 일치한다.

마지막 두 조건은 동일 초기 로비 카메라, 한 개 게임 탭, 1280×720 브라우저·1920×1200 출력, Host 1명이다. 양쪽 모두 로컬 HTML에서만 pointer lock 요청을 우회해 카메라가 돌아가는 것을 방지했다. 게임 실행 코드·프레임 루프는 동일하다. 아래 두 표본씩은 각 30초이며, 3D 크기는 표본 시작 시점의 렌더 타깃 관측이다.

| 조건 | 3D 타깃 관측 | 평균 FPS | p95 / p99 (ms) | 33.3ms 초과 |
|---|---|---:|---|---:|
| 강제 저해상도 1 | 360×225 | 58.10 | 24.4 / 31.5 | 0.40% |
| 강제 저해상도 2 | 360×225 | 60.72 | 22.2 / 23.9 | 0.00% |
| 유지할 최종 설정 1 | 1343×839 | 64.19 | 21.2 / 24.0 | 0.05% |
| 유지할 최종 설정 2 | 1247×779 | 64.39 | 20.8 / 22.7 | 0.05% |

강제 시험은 URP 기본 배율 0.375에 동일 자동 조절을 적용한 진단이다. 실제 배율이 0.1875까지 내려가 물건·월드 공간 글씨가 심하게 흐려졌다. Overlay UI 출력은 유지됐다. 이렇게 줄여도 최종 설정보다 좋아지지 않아 제품 하한을 더 낮추지 않는다. 이는 "큰 해상도가 더 빠르다"는 일반 법칙의 증거가 아니라, 현재 비용이 픽셀 수에만 비례하지 않으며 이 변경의 채택 근거가 부족하다는 뜻이다.

기본 배율 0.75 탐색 표본은 68.13FPS였지만 실제 3D 타깃이 1440×900으로, 목표로 한 기존 하한 이하 대조가 아니었다. 별도 초기 저해상도 표본은 카메라 방향이 달라 직접 비교에서 제외했다. 이전 최종 플레이어 재실행은 61.17 / 58.24FPS, 더 이른 안정 표본은 52.34FPS였다. 따라서 최종 두 번의 약 64FPS만 골라 전 환경·전 경기에서 60FPS를 보장하지 않는다.

### 적용과 미확정 범위

- 적용 유지: WebGL 전용 3D 자동 배율, 화면 공간 그림자 프로필, 일반 빌드 RuntimeSpeed 명시. 기존 Host·물리·네트워크 판정과 Overlay UI·조명·그림자 설정 보존.
- 추가 채택 없음: 극단적인 저해상도, 브라우저 프레임 스케줄러 변경, 조명·그림자 제거. 두 시험용 RP 기본 배율은 원복했다.
- 정상 플레이어 빌드 성공 및 기존 EditMode 19개 통과. 추가 에셋 대조 빌드도 각각 171.35초·177.83초에 성공했다. 최종 측정 탭에서 error 레벨 브라우저 로그는 없었다.
- 원래 PC 설정에 대한 생성 노이즈, 로컬 HTML 계측·pointer lock 우회를 원복하고 진단 탭을 종료했다. 실험 원본 결과와 해시는 `.build/lobby-profiler/final-extra-comparison.json`에 보관했다.
- 이번 관측은 로컬 Chromium IAB의 혼자 있는 로비다. 사용자 Chrome의 3~6인 경기·모든 상호작용 회귀와 공개 배포 성능은 미검증이다. MR·배포는 실행하지 않았다.

### 현재 결론

로비의 클라이언트 렌더링 부담을 줄이는 변경을 마련했고, 최종 반복은 약 64FPS / p95 약 21ms였다. 다만 앞선 52~61FPS 표본이 있어 "완전히 해결"이나 "고정 60FPS"는 입증하지 못했다. 픽셀 수를 극단적으로 낮춰도 개선이 이어지지 않아, 추가 저해상도만으로 남은 프레임 시간을 해결할 수는 없었다.

렌더 타깃 관측상 2048²·4096² 그림자 맵 등의 비용은 3D 배율과 함께 줄지 않는다. 이는 남은 후보이며, 이번 대조만으로 CPU 렌더 명령 제출·그림자 GPU 처리·브라우저 스케줄링 각각의 비율까지 분리한 것은 아니다. Host 서버가 주원인이라고 확정하거나 서버 증설로 해결된다고 말할 근거는 없다. 더 진행할 경우 같은 Chrome·실제 경기에서 GPU 시간과 CPU 렌더링 제출 비용을 분리 측정한 뒤, 기능을 보존하는 그림자/지오메트리 처리 변경을 판단해야 한다. 이번 시간 제한 안에서 이 세부 분리와 실전 검증까지 완료했다고 주장하지 않는다.
